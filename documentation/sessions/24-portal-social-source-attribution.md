## Objective
The user wanted to funnel all social-media traffic into the customer portal. The opening ask was purely a writing task — *"I want to promote this link to our Social Media Manager for Promotion — https://customers-apmg-services.vercel.app/portal … I want you to give me an email message making sure that every post she ever posted on tiktok instagram and facebook includes this link please in a nice gentle manner"*. After the draft, the reply offered per-platform `?utm_source=` links as an optional upgrade, and the user took it: *"Can we also prepare for this where we can see all the leads coming from whether if its from Facebook or Tiktok and Instagram?"* — which turned the session into building traffic-source attribution end to end, before the social manager starts posting.

## TL;DR
- **The email was drafted first** — a gentle, per-platform note (Facebook captions are editable, Instagram needs link-in-bio + a "link in bio" caption line, TikTok needs a pinned comment because captions can't be edited). It lives in the transcript only; **no repo file** and it was **not sent** from here.
- **New `lib/portal/source.ts`** — the whole attribution vocabulary in one pure-string module: the `apmg_src` cookie name, a 30-day max-age, alias folding (`fb`/`meta`→`facebook`, `ig`/`insta`→`instagram`, `tt`/`tik-tok`→`tiktok`, `twitter`→`x`, …), a social-Referer host map, `resolveSource()`, and the `outreach` / `direct` reporting buckets. Deliberately free of node/next imports so the **Edge middleware, the node API routes and client components can all import it**.
- **Capture in `middleware.ts`** — a `/portal` **page** load carrying `?utm_source=` (or `source`/`src`/`ref`), or arriving with a recognised social Referer, drops an httpOnly `apmg_src` cookie. API paths are skipped; an untagged visit leaves an existing cookie alone; a fresh tagged visit re-attributes (**last touch wins**). The customer-host bare-domain redirect **already** carried the query string through to `/portal` (it clones `req.nextUrl`), so `…vercel.app?utm_source=tiktok` keeps its tag — this session only pinned that down with a comment, and then proved it in the smoke test (`307` → `location: /portal?utm_source=facebook`).
- **Stamping is server-owned.** `readAttribution()` in `lib/portal/server.ts` now returns `source` alongside `leadId`/`campaign`, re-normalised so a hand-crafted cookie can't smuggle text into reports. The events sink **deletes any client-supplied `props.source`** before stamping its own; the enquiry route nulls the source for operator/bot submissions.
- **Storage degrades instead of failing.** A new `isMissingColumn()` helper (PostgREST `PGRST204` on insert / `42703` on select) lets the enquiry insert, the enquiry listing and the summary aggregation each **retry without `source`** when the migration hasn't been run — an enquiry must never be lost over an analytics column.
- **Reporting** — `/api/portal/summary` gained a `bySource` rollup (visitors / views / enquiries) with the precedence *explicit source → `outreach` (has an `apmg_ref` lead cookie) → `direct`*, so social is directly comparable to the email campaigns.
- **UI** — the Enquiries tab gained a **"Where they came from"** panel and a **"via TikTok"**-style `SourceChip` on enquiry rows; `sourceLabel()` + `SOURCE_LABEL` give the slugs display names; demo data updated to match.
- **Verified** — `tsc --noEmit` clean and `next build` passes (which validates the Edge middleware bundle that now imports the new module), though both ran on a working tree a **concurrent** session had already patched (see Problems). The smoke test against a **local** production server ran five cases and all five behaved: tagged link → `apmg_src=tiktok`; **alias** `?utm_source=ig` → `instagram`; **untagged Instagram Referer** → `instagram`; a plain untagged visit → **no cookie at all**; customer-host `GET /?utm_source=facebook` → `307 location: /portal?utm_source=facebook`.

## Narrative

The session opened as a copywriting request and stayed there for one turn: a ready-to-send email to the Social Media Manager, gentle in tone, praising her existing content, then asking for the portal link on every post — new ones now, the back catalogue "whenever you get a chance". The platform-specific detail was the useful part, because the three networks behave differently: Facebook captions can be edited retroactively, Instagram captions don't make links tappable (so link-in-bio plus a "link in bio 👆" line), and TikTok captions can't be edited after posting at all (so a pinned comment with the link). The draft closed with an optional idea — hand her three slightly different links (`?utm_source=tiktok` / `instagram` / `facebook`) so portal traffic isn't one undifferentiated blob — with the honest caveat that it wasn't known yet whether the portal captured query params.

The user asked for exactly that, so the next move was to find out. Reading `app/api/portal/events/route.ts`, `lib/portal/server.ts`, `lib/telemetry.ts`, `app/api/portal/inquiries/route.ts`, `app/api/portal/summary/route.ts`, `middleware.ts`, `supabase/portal-telemetry.sql` and the Enquiries page showed the shape of what already existed: an `apmg_ref` / `apmg_ref_campaign` cookie pair dropped by the `/t/[id]` outreach redirect and read by `readAttribution()`, with events and enquiries enriched from it. Nothing anywhere read `utm_source`. So the design wrote itself — a **third cookie riding the same rails as the outreach ones**, rather than a parallel mechanism.

`lib/portal/source.ts` was written first, and its constraint drove its shape: `middleware.ts` runs on the **Edge runtime** and client components need the label logic, so the module is pure string helpers with no node or next imports (the display labels themselves live in `lib/data/enquiries.ts`, which is client-safe). It carries the cookie name and max-age, an alias table so "fb", "FB" and "facebook" don't split one platform across three report rows, a hostname regex map for the Referer fallback (including the wrappers the social manager can't tag — `l.instagram.com`, `vm.tiktok.com`, `t.co`, `lnkd.in`, `youtu.be`), and `normalizeSource()`, which lowercases, slugifies, strips to `[a-z0-9_.-]`, caps at 40 chars and returns `null` when nothing usable remains.

Capture went into the existing host-wall middleware as a small `withPortalSource()` wrapper applied at the two portal-reachable `NextResponse.next()` returns (the third `next()` — the branch that stamps the operator's `apmg_internal` cookie on admin page loads — is deliberately left alone). It fires only on `/portal` page loads — the source of a beacon is whatever the *page* visit established, so API paths are skipped — and it no-ops when there's no source or when the cookie already holds the same value. The customer-host redirect that sends stray paths to `/portal` was left cloning `req.nextUrl`, which means a promoted link to the bare domain keeps its tag through the redirect; that behaviour got a comment so it isn't optimised away later.

Then the read side. `readAttribution()` was extended to a third return field, parsing `apmg_src` off the same raw Cookie header walk and passing it back through `normalizeSource()` — the cookie is httpOnly, but re-normalising means even a forged one can only ever produce a harmless slug. In the events sink the stamping is explicitly **server-authoritative**: `sanitizeProps()` runs, then `delete props.source`, then the cookie value is written in if present. A crafted beacon therefore cannot misfile traffic under a platform it didn't come from. The existing operator (`apmg_internal`) and bot User-Agent drops in that route were left untouched, so the new numbers inherit the same honesty guarantees as the old ones.

The enquiry route was the fiddly one, because it writes a real PostgREST row and the `source` column wouldn't exist until the user re-ran the migration. Rather than make the feature depend on an ops step, `isMissingColumn()` was added to `lib/portal/server.ts` (matching `PGRST204`, `42703`, `column … does not exist`, `Could not find the … column`) and used in three places: the insert retries with `source` deleted from the row, the admin listing retries with a `LEGACY_COLS` select, and the summary route retries with `LEGACY_INQUIRY_COLS`. Each path logs a "run supabase/portal-telemetry.sql" reminder. The source also rides in `props` on both server-emitted events (`portal_consent_accept` and `portal_inquiry`) so the funnel aggregation can group uniformly, and it was added to the n8n enquiry-notification payload.

`supabase/portal-telemetry.sql` got the column in the `create table` body *and* a standalone `add column if not exists` for tables that pre-date it. `portal_events` needed no change at all — the source rides in its existing `props` jsonb, which is noted in a comment so nobody adds a redundant column later.

The summary route then grew a `bySource` map next to the existing `byService` / `byCategory` ones, keyed by a small `channelOf(source, leadId)` helper that encodes the precedence decision: an explicit social source wins, otherwise a lead-attributed row files under `outreach`, and everything else under `direct`. Visitors are counted as a `Set` of `visitor_id` per bucket, views come from `portal_view` events, and enquiry counts come from `portal_inquiries` (the canonical store) rather than from events.

The UI followed: types and the `SOURCE_LABEL` map in `lib/data/enquiries.ts`, a `bySource` array on `PortalSummary`, `source` on `PortalInquiry`, and the demo dataset updated so the numbers reconcile (one demo enquiry set to `tiktok`, a `bySource` block where outreach still dominates and the social rows are starting to move). ## Decisions
- **A cookie, not a per-request query param.** The tag only exists on the first click; a 30-day httpOnly cookie means "saw the TikTok, enquired from the couch a week later" still attributes, and every subsequent event/enquiry inherits it without the client having to carry state.
- **Ride the existing attribution rails.** `apmg_src` is read by the same `readAttribution()` walk as `apmg_ref` / `apmg_ref_campaign`, so social attribution inherits the outreach path's normalisation, bot/operator filtering and enrichment rather than duplicating them.
- **Last touch wins.** A fresh tagged visit overwrites the cookie; untagged visits leave it alone. Stated explicitly to the user as a judgement call rather than buried.
- **Source is server-owned.** Client-supplied `props.source` is deleted before stamping, and the cookie value is re-normalised on read. The browser can suggest nothing about where it came from.
- **Pure-string module.** No node/next imports in `lib/portal/source.ts` because the Edge middleware imports it — validated by the production build, not assumed.
- **Referer fallback, not utm-only.** Instagram and TikTok bio links can't always be tagged, so recognised social hostnames (including short-link wrappers) attribute anyway.
- **Alias folding.** `fb` / `meta` / `ig` / `insta` / `tt` / `tik-tok` fold onto canonical slugs so one platform can't split into several report rows.
- **Open-ended slugs, not an enum.** Any future `utm_source` value (e.g. `newsletter`) simply becomes its own row, with `sourceLabel()` title-casing unknown slugs.
- **Never lose an enquiry over an analytics column.** All three DB paths retry without `source` on a missing-column error and log a reminder, instead of the feature hard-depending on the user running SQL.
- **`outreach` / `direct` as first-class buckets.** Without them the panel would only show social and the user couldn't answer "is the social push worth it *compared to* the email campaigns".
- **No column on `portal_events`.** The source rides in the existing `props` jsonb — noted in the SQL so nobody adds a redundant one.
