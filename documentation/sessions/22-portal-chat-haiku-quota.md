## Objective
In the user's framing: *"Based on our documentation on our knowledgebase folder I want you to connect our AI Assistant for the customer facing portal to be connected to Haiku please also limit each User that clicked it via the Email to 10 Prompts the last prompt should direct them to give us their contact info and like Enquire to the services. Add guardrails to this as much as possible we dont want any abuse on our API tokens on this."*

Three asks, one worry: (1) portal chat bubble on Haiku, grounded in the knowledgebase folder; (2) a **10-prompt cap per person who arrived via a tracked outreach email**, with the 10th prompt turning into a contact-capture moment; (3) as many abuse guardrails as possible, because the endpoint is public and spends a paid Anthropic key. The user's follow-up (*"do we need to fix anything?"*) turned the end of the session into a ship-readiness audit rather than more building.

## TL;DR
- **Haiku was already wired.** `lib/ai/portalChat.ts` was on `claude-haiku-4-5` with the walled-off `PORTAL_CHAT_ANTHROPIC_KEY` and grounded on `components/knowledgebase/business.md` **before** this session (the chat module and its Haiku wiring date to commit `3d14dbc`, 2026-07-19; `business.md` itself is older still — `8987177`, 2026-07-04). This session verified and kept that, and added Anthropic `metadata.user_id` for provider-side abuse grouping. The honest answer to "connect it to Haiku" was "it already is."
- **New durable quota** in `lib/portal/chatQuota.ts`: `PROMPT_LIMIT = 10` prompts **total** per visitor identity (the constant itself lives in the shared `lib/portal/chatLimits.ts`). An email-click visitor is identified by the httpOnly `apmg_ref` cookie set by `/t/[id]` — **validated against a real `public.leads` row** — and counted durably as one `chat_prompt` row per prompt in `portal_events` (same server-canonical ledger pattern as `email_sent`). **No migration:** it reuses the existing `portal_events` table.
- **Final prompt = lead capture.** On prompt 10 a `FINAL_TURN_NOTICE` system block tells the model to answer briefly then invite the visitor to tap **Enquire** and leave contact details. Prompt 11+ gets a fixed `LIMIT_REACHED` CTA string with **zero model spend**, and the client composer locks.
- **Eight-gate guardrail chain** in `app/api/portal/chat/route.ts`, in order: (1) sameOrigin → (2) bot/scanner filter → (3) per-IP window (15 / 10 min) → (4) input caps (1,000 chars, 12 history turns; the 400-token reply cap is applied in `lib/ai/portalChat.ts`, not the route) → (5) configured-key check → (6) daily-budget **peek** (6a) plus the lifetime quota slot (6b) → (7) daily circuit-breaker **claim** → (8) KB-only system prompt. Nine steps, eight numbered gates — the peek and the quota share gate 6 in the route's own numbering.
- **`PORTAL_CHAT_DAILY_CAP`** is a per-instance model-calls-per-UTC-day breaker, default `300`, and **`0` is honoured as a kill switch** (the first draft silently treated `0` as 300).
- **A 27-agent adversarial review workflow** ran in the background and found real holes. Its log records **"17 confirmed, 6 refuted of 23 findings"**, and those 17 verdicts collapse to **exactly 13 distinct defects** — the number quoted in the session's own closing summary (re-checked against the workflow's confirmed list on 2026-07-30; see *Problems* below for the arithmetic). The two worst were fixed: `apmg_ref` was trusted **on shape alone** (rotating random UUIDs would mint unlimited fresh allowances), and the `apmg_internal` operator cookie was a **self-settable quota bypass**.
- **Client UX mirror** in `PortalChat.tsx`: `remaining` / `limitReached` come back on every reply that actually spent a slot (success + model-failure fallback), the composer disables with "Chat limit reached — tap "Enquire" above", a hint appears at ≤2 remaining ("N questions left", or "That was your last question." at 0), and `portal_chat_limit_reached` telemetry fires.
- **Not done:** no live end-to-end test (no run against the real key), `PORTAL_CHAT_DAILY_CAP` is undocumented in `.env.local.example`, and several residuals were deliberately accepted rather than fixed.

## Narrative
The session opened by loading the `claude-api` skill (since Haiku was the subject), then mapping the terrain: the chat route, `/t/[id]`, the knowledgebase folder, `lib/portal/server.ts`, `lib/portal/chatRateLimit.ts`, `supabase/portal-telemetry.sql` and the chat bubble component (`middleware.ts` came later, mid-review — see below). The first finding was that the request was partly already satisfied — the assistant was on `claude-haiku-4-5`, spending a second key (`PORTAL_CHAT_ANTHROPIC_KEY`) deliberately isolated from the outreach composer's `ANTHROPIC_API_KEY`, and grounded on `business.md`. It already had a sameOrigin floor, a per-IP sliding window (15 / 10 min), message-length and history caps, and a KB-only system prompt. What it had **no** concept of was a per-person lifetime allowance.

The design question was "who is a user?" The user's phrasing — *"each User that clicked it via the Email"* — pointed straight at the existing attribution cookie: `/t/[id]` sets httpOnly `apmg_ref` with the lead UUID when an outreach CTA is clicked. That gave a natural durable key. Rather than a new table, the count was written as `chat_prompt` rows into `portal_events`, mirroring the `email_sent` ledger already in use — so no SQL migration was needed at all, which was stated plainly instead of inventing one.

The first pass built `lib/portal/chatQuota.ts` (identity + count + record + daily breaker), rewrote the chat route around it, added `PROMPT_LIMIT` to the shared `chatLimits.ts`, added the `FINAL_TURN_NOTICE` block to `portalChat.ts` **after** the KB cache breakpoint (so appending it can't invalidate the cached prefix), reserved `chat_prompt` in the events sink's forbidden-name set, and locked the client composer. One ordering bug was caught immediately by re-reading the route: the daily-cap check sat **after** the visitor's slot was consumed, so an exhausted day would silently burn a legitimate lead's allowance. It was moved ahead of the reservation.

Typecheck was clean, so a **27-agent adversarial review workflow** (4 review agents fanning out into 23 verification agents) was launched in the background with the change's stated intent as context. While it ran, `middleware.ts` was read to answer a nagging question: how is `apmg_internal` actually set? The answer was damning — middleware only sets it httpOnly on **non-customer** hosts, so a portal visitor has no protecting cookie and can simply `document.cookie` themselves an `apmg_internal` value. The first draft had treated that cookie as a full quota **bypass** so the operator could test freely. That was rewritten on the spot: internal browsers are now **demoted to the anonymous IP path** (counted in memory, never written to the ledger, so `portal_events` stays customer-activity-only per the project's telemetry rules) — but they get no extra spend. Typecheck re-run, clean.

The review then landed, and it was blunt. The headline finding was that `apmg_ref` was promoted to a `lead` identity on `isUuid()` alone — no existence check — so a caller rotating random UUIDs got a fresh 10-prompt allowance *per request*, and each one also wrote junk `chat_prompt` rows against non-existent `lead_id`s (`portal_events` has no foreign key). The fix was to require `lookupLead()` to resolve a real row before granting lead identity; a miss falls through to the strictly-narrower IP bucket. That lead snapshot is now reused by `recordChatPrompt` so the ledger row carries category without a second fetch.

Several other confirmed findings were fixed in the same pass, and the quota module and route were rewritten wholesale rather than patched:
- **A missing/revoked key permanently burned durable slots.** `recordChatPrompt` ran before the model call by design (so a crash mid-call can't hand out a free retry) — but with no key configured, *every* attempt wrote a ledger row while the visitor only ever saw the generic fallback, eventually locking a real lead out of chat forever. Fixed with a new exported `isChatConfigured()` checked **before** any allowance is touched.
- **The daily-cap branch reported `remaining` one lower than reality.** Split into a `dailyBudgetExhausted()` **peek** before the slot is claimed (returning no `remaining` at all, because nothing was consumed) and a `takeDailySlot()` claim after it, with `releaseChatSlot()` handing the reservation back if the day races to zero in between.
- **Fallback replies omitted `limitReached`,** so when the model failed on the visitor's final prompt the slot was spent but the composer stayed unlocked. The `!reply` branch now carries `remaining` and `limitReached` too.
- **`PORTAL_CHAT_DAILY_CAP=0` silently meant 300.** The first draft's guard was `Number.isFinite(raw) && raw > 0 ? Math.floor(raw) : DAILY_CAP_DEFAULT`, so an explicit `0` (and any negative) fell back to the 300 default — while, absurdly, `0.5` floored to `0` and *did* disable chat. Now `raw >= 0`, so `0` is a genuine kill switch — the property the code's own comment claimed.
- **A crafted or buggy history could guarantee an API 400** (assistant-first conversation, or empty-content turns) *after* the quota slot was already spent. A `rawHistoryToTurns()` sanitizer now drops empty turns and shifts leading assistant turns, so a bad history degrades to a smaller prompt instead of a guaranteed-failed call.
- **`email_sent` was still forgeable from the public beacon sink** — an adjacent pre-existing hole the reviewers spotted while looking at the edited reserved-names set. Added to `SERVER_RESERVED_EVENT_NAMES` alongside `chat_prompt`.
- **The `cache_control` marker on the KB block never actually caches.** Haiku 4.5's minimum cacheable prefix is 4096 tokens and instructions + `business.md` measure well under that, so the breakpoint is a silent no-op — meaning the cost rationale written in the comments was fiction. The marker was kept (it engages for free the day the KB grows) but the comments were corrected to say so, and the "cached KB prefix" justification was stripped out of the daily-cap comment.

Same-instance double-spend was closed structurally: `openChatSlot`'s memory check-and-reserve is **synchronous** (no `await` between read and write), so two concurrent requests on one instance can't both take the last slot. Cross-instance serverless races were documented as an accepted residual rather than papered over.

Mechanically, the tail of the session was fiddly. The workflow ran in the background, so a fallback `ScheduleWakeup` heartbeat was armed in case its completion notification never arrived (and cancelled at the end). Pulling the full verify verdicts out of the workflow journal took four Bash attempts: two `cd`-into-the-workflow-dir Python invocations came back with nothing but "Shell cwd was reset", an absolute-path `head` call proved the journal was readable, and a retry of the same `cd`-plus-heredoc shape then returned the verdict text. The final typecheck was clean, and the architecture was written to agent memory as `portal-chat-guardrails.md`.

The closing exchange (*"do we need to fix anything?"*) produced an honest ship-readiness list rather than more code: confirm the key is set on the customer-portal Vercel project, note that no migration is needed, admit no live smoke test was run, and put three accepted trade-offs in front of the user for veto.

## Decisions
- **Reuse `portal_events` as the quota ledger — no migration.** One server-written `chat_prompt` row per accepted prompt, matching the existing `email_sent` pattern. A dedicated table for a counter that maxes out at 10 rows per lead would be dead weight, and the user was told this plainly rather than handed a migration they didn't need.
- **Identity is "validated lead, else IP" — narrower, never wider.** The `apmg_ref` cookie must both parse as a UUID **and** resolve to a real `public.leads` row. Any miss (forged cookie, stale cookie, deleted lead, transient Supabase error, Supabase not live) falls back to the IP bucket. The cookie is client-supplied, so shape alone can never be trusted.
- **The `apmg_internal` operator cookie is demoted, not exempted.** It is an unauthenticated marker a visitor can set on themselves, so it must never unlock spend. Demoting it to the anonymous IP path keeps operator testing out of the customer-only `portal_events` ledger *and* gives the cookie zero attack value — behaviourally identical to a visitor clearing their cookies.
- **Reserve the slot before the model call.** A crash or timeout mid-call must not hand out a free retry. The corollary — that a deterministic failure would burn slots for nothing — is why the configured-key check sits ahead of the reservation.
- **Peek the daily budget before claiming the visitor's slot.** During an exhausted day (abuse wave, viral spike) the route bails without touching Supabase or the visitor's allowance, so legitimate leads keep their prompts for tomorrow. If the budget races to zero between peek and claim, the reservation is released.
- **The in-memory reserve is synchronous.** No `await` between reading and writing the counter, so same-instance concurrency cannot double-spend the last slot. Cross-instance races are accepted (see below) — this is spend protection, not billing.
- **Ledger failures degrade to the in-memory count, never to "unlimited."** Whichever count is **higher** wins.
- **`PORTAL_CHAT_DAILY_CAP=0` is a kill switch.** An explicit zero means "no model calls at all"; negative or unparsable values fall back to 300. Chosen so there is a single-env-var panic button that needs no deploy of new code.
- **Client-side locking is UX only.** Every limit decision is made server-side; the composer lock exists so the visitor isn't invited to type into a dead box.
- **Keep the `cache_control` marker even though it's currently a no-op** — it costs nothing and engages automatically once the cached prefix (system instructions + KB, ~1.5–1.7k tokens today) passes 4096 tokens. But say so in the comment rather than claiming savings that don't exist.
- **Knowledgebase grounding left as-is:** the chat loads only `components/knowledgebase/business.md`, not the sector files (`aged-care.md`, `early-childhood.md`, `education.md`). That was pre-existing behaviour and was not changed this session, despite the request naming the folder.

## Problems / gotchas
- **`apmg_ref` was trusted on shape alone in the first draft** — the single worst hole. Any caller rotating random UUIDs minted a fresh 10-prompt allowance per request, and each one wrote junk `chat_prompt` rows against a non-existent `lead_id` (the table has no foreign key, and the service-role key bypasses RLS). Fixed with the `lookupLead` existence check.
- **`apmg_internal` started life as a real bypass.** Reading `middleware.ts` revealed the cookie is only set httpOnly on non-customer hosts, so a portal visitor can self-set it. Rewritten to demote rather than exempt.
- **A missing key would have permanently locked leads out of chat.** Because the ledger write preceded the model call, an unset `PORTAL_CHAT_ANTHROPIC_KEY` burned durable slots on calls guaranteed to fail. Caught by review; fixed with `isChatConfigured()`.
- **Two off-by-one / state-leak bugs on the response shape** — the daily-cap branch reported `remaining` as if the prompt had been consumed, and fallback replies omitted `limitReached`, leaving the composer unlocked after the final prompt was spent. Both fixed.
- **`PORTAL_CHAT_DAILY_CAP=0` silently meant 300** because the guard tested `raw > 0` (not `>= 0`) before falling back to the default, directly contradicting the comment that called it a kill switch.
- **The prompt cache was decorative.** Haiku 4.5 needs a ≥4096-token prefix; instructions + `business.md` come to roughly 1.5–1.7k tokens, so `cache_control` is silently accepted and never hits. Comments were corrected — **but one stale claim survives**: the `SYSTEM_INSTRUCTIONS` docblock in `lib/ai/portalChat.ts` still reads *"appended as a `cache_control` block so repeat visitors reuse it at ~0.1x input"*, which now contradicts the corrected note further down the same file. Cosmetic, but it's the kind of comment that misleads the next reader.
- **Review scoreboard — resolved, both numbers are right.** The workflow's own log line reads **"17 confirmed, 6 refuted of 23 findings"** (4 review agents → 23 verification agents → 27 agents total, matching the workflow's `agentCount`); the session's closing message said "13 confirmed findings." Re-reading the workflow's confirmed list on 2026-07-30 settles it: the `remaining` off-by-one was reported three times and the cache and `limitReached` findings twice each, so 17 − 2 − 1 − 1 = **exactly 13 distinct defects**. "17" counts verdicts, "13" counts defects.
- **A factual slip in the closing summary.** The user was told `chat_prompt` rows "will show in the Telemetry tab's lead trails." They will **not** — `ATTRIBUTED_EVENT_NAMES` in `app/api/portal/lead-activity/route.ts` does not include `chat_prompt`, so the lead-activity trail filters them out. They *do* land in the unfiltered 2000-row window that backs `/api/portal/summary`, which is the dilution the reviewers actually flagged and which was **not** fixed. The offered "one-line filter in the summary route" was never applied.
- **A second slip in the closing summary: the cost figure.** The user was told the default 300-call cap is "≈ under $1/day worst case at Haiku pricing" (twice), and `chatQuota.ts` still calls it "pocket change". Worked out against Haiku 4.5's published $1 / $5 per-MTok input/output rates, that is not the worst case: 300 calls with the 12-turn history cap filled and 400-token replies is roughly **$1.60–$2.00/day** (the review's own verifier computed ~$1.00 input + ~$0.60 output). Sub-$1/day only holds for realistic traffic — short 1–3-sentence replies and light history land nearer **$0.60/day**. Either way it was never checked against an actual bill.
- **Accepted residuals, deliberately not fixed:**
  - **Cookie-clearing buys one extra batch.** A visitor who wipes `apmg_ref` (or self-sets `apmg_internal`) drops into the shared IP bucket for up to 10 more prompts per (IP, warm instance). Closing it fully needs real visitor auth; spend stays bounded by the window limiter and the daily cap — both per-instance, so read that bound with the caveat two bullets down.
  - **Anonymous counts reset on cold starts,** and the FIFO eviction in `bumpMemory` (at 10,000 tracked keys) can zero an active IP's count. Only email-click leads get the durable count — which is exactly the group the user asked to limit.
  - **Cross-instance count-then-insert race** can overshoot the cap on a simultaneous burst, and the same window can hand out the 10th prompt without the model-delivered final-turn CTA (a separately reported confirmed finding, same root cause). The mitigation the code cites is weaker than it reads: the reviewers noted `RATE_LIMIT = 15` is itself *above* `PROMPT_LIMIT = 10`, and the window limiter and daily breaker are per-instance too, so on a multi-instance burst neither bounds the overshoot tightly. Accepted as a spend-shaped, not billing-shaped, guarantee.
- **No live smoke test.** Everything was verified by `npx tsc --noEmit` (three clean runs) and adversarial code review only. Nothing was ever run against the real key, Supabase, or a real tracked link.
- **Background-workflow plumbing friction.** The review ran detached with a `ScheduleWakeup` heartbeat as a fallback (later cancelled); extracting the full verify verdicts from the workflow journal took several Bash attempts because `cd`-plus-heredoc invocations kept reporting the shell cwd being reset.
