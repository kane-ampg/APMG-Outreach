## Narrative
The session opened with the user pasting three social URLs and asking for them on the customer portal, with an explicit instruction to use the marketing skill. The assistant invoked `marketing-skills:cro` and treated the request as a trust-signal problem rather than a decoration problem: a cold-outreach recipient decides in seconds whether the business is real, and live third-party profiles are checkable proof in a way on-page copy is not. (Worth being honest about what that skill actually contributed: it was loaded and then never exercised as an analysis — no page-type / conversion-goal / traffic assessment and no recommendation list were produced in-session. The trust-signal reasoning survives only in the code comments the assistant wrote.)

The logo half of the request needed diagnosis before implementation. A `public/**/*logo*` glob found **nothing**, which initially looked like the logo was genuinely absent. Grepping the imports in `ServicesPortal.tsx` showed the real source — `import brandLogo from "@/app/icon.png"` (the favicon asset, reused as the hero mark) — and reading the hero showed the `<Image>` was already there, but nested inside the `absolute inset-0 … justify-end` copy stack with `self-start`. In practice that put it above the eyebrow badge but still down in the bottom-weighted block over the hero photo, which is why it did not read as "present at the top." So the change was a **move, not an addition**.

Before writing anything, the assistant checked two contracts. First, the telemetry contract: `lib/telemetry.ts`'s `useClickTelemetry` attaches one capture-phase delegated listener that lifts every `data-track-*` attribute into props (`data-track-network` → prop `network`), and it is mounted in both `PortalStandalone` (view `"portal"`) and `DashboardShell`. Second, whether the events sink would accept new names — `app/api/portal/events/route.ts` was read and confirmed to use `EVENT_NAME_RE` plus a `SERVER_RESERVED_EVENT_NAMES` **denylist** (`attribution_click`, `portal_inquiry`, `portal_consent_accept`, `chat_prompt`, `email_sent`), so arbitrary client names pass. No route edit was needed.

Implementation went constants → component → surfaces: `COMPANY.socials` first (so the URLs have one home alongside phone/address/ABN), then `SocialLinks.tsx`, then the hero top bar, then the customer footer's contact row, then the footer doc comment so the "what this footer carries" list stayed accurate.

The hero top bar needed a second pass, and the raw session JSONL shows exactly what that pass changed. The first edit (08:12:24 UTC) created the bar as `absolute inset-x-0 top-0 flex items-start justify-between` — no `z-10`, no pointer-events handling at all. After the first typecheck the assistant re-read the block (08:13:21) and edited it again (08:13:43), adding precisely three things: `pointer-events-none` + `z-10` on the bar container, `pointer-events-auto` on the `SocialLinks` `linkClassName`, and the comment tail explaining both. The reasoning it wrote down: the bar sits **earlier** in DOM order than the `inset-0` copy stack that follows it, so without `z-10` that stack paints over the bar and swallows clicks on the icons; and because the bar is full-width, without `pointer-events-none`/`auto` it would in turn intercept clicks meant for the copy stack's own CTA row.

## Decisions
- **URLs in `company.ts`, not in the component.** Same rule the phone, address, WhatsApp deep link and Google-reviews URL already follow. The type comment states the constraint explicitly: *"Live pages only — a dead social link on a trust surface reads worse than no link at all."*
- **Inline simple-icons SVGs, not an icon package.** Copies the documented `WhatsAppIcon` decision (lucide deliberately ships no brand icons; a generic glyph loses the recognition the link exists for). No new dependency.
- **Display order Facebook → Instagram → TikTok**, not the paste order. This is a real, small divergence from the request and is not flagged anywhere as a deliberate choice — checked against the **full raw transcript**, not just the condensed record: no user or assistant statement mentions ordering at all. It is simply the order written into `COMPANY.socials`, and trivially reorderable in one place.
- **Move the logo, don't duplicate it.** One `<Image src={brandLogo}>` relocated from the bottom stack to the top bar, so there is no second mark to keep in sync.
- **Top bar click-transparent except the icons.** `pointer-events-none` on the container, `pointer-events-auto` on each link, `z-10` on the bar — the bar is full-width and earlier in DOM than the CTA stack, so anything else would have cost clicks in one direction or the other. Not part of the first edit: it was a self-review fix on the second pass.
- **Modal instead of navigation for legal links, but keep the pages.** The shareable/bookmarkable URLs were an explicit earlier design goal, so they stay live and the modal links out to them rather than replacing them.
- **One source of policy text.** The modal reads the same `/api/portal/legal` the enquiry consent pins, so the text shown can never diverge from the text consented to. No second copy of the policy in the codebase.
- **Honest fallback over boilerplate.** `placeholder: true` *or* a failed fetch both render the "being finalised, contact us at…" copy with a live mailto/tel — matching `LegalDocPage`'s existing rule.
- **Lazy fetch on first open.** The footer renders on every portal view; the policy is only needed if someone actually looks.
- **No new server-side event names.** Both new events are client-emitted through the existing declarative `data-track` path, so the `SERVER_RESERVED_EVENT_NAMES` denylist stayed as-is.
