## Objective
One user message, no follow-ups:

> "Leads tab please add an export button please so I can export them even on the folders outside but definetely if we are exporting them each folder gets a different sheet"

Two distinct asks inside it:
1. The Leads tab's **folder grid** — the "outside" view you land on before opening a folder — had **no Export button**. Only the inside-a-folder / search-results table had one.
2. When an export spans more than one import folder, **each folder must land on its own sheet**.

## TL;DR
- **The exporter already existed.** `lib/pipeline/leadExport.ts` and `components/apmg/pipeline/LeadsExport.tsx` were **not created here** — they were committed two weeks earlier in `a020319` "Save to PDF" (2026-07-15) with CSV + XLSX + PDF already working. This session added **folder splitting** to all three formats and put an **Export button on the folder grid**.
- **Zero new dependencies.** The XLSX writer is still hand-rolled OOXML (inline strings + a stored/uncompressed ZIP built with a local CRC-32 table) — no `xlsx`/`exceljs`/`jszip` was added. Multi-sheet support was achieved by parameterising the existing single-sheet writer, not by importing a library.
- **New folder-grouping primitives** in `leadExport.ts`: `groupLeadsByFolder()` (alphabetical, `Ungrouped` last) and `leadFolderCount()`, plus `safeSheetName()` enforcing Excel's sheet-name rules (replace `[ ] : * ? / \` with **spaces** — not delete them — collapse whitespace, truncate to 31 chars, fall back to `Sheet N` if nothing survives, de-dupe with a ` (2)` suffix, case-insensitive uniqueness).
- **All three formats honour the split**, each as far as the format allows: XLSX gets one worksheet per folder; CSV stays one file but orders rows folder-by-folder (the existing `Folder` column carries the identity); PDF gets a banded uppercase heading row per folder, numbered within the folder.
- **Single-folder exports are unchanged** — still one sheet literally named `Leads`, no headings in the PDF, original row order in the CSV. The split only engages when `groups.length > 1`.
- **The popover became self-describing** — on a multi-folder scope the folder count *replaces* the scope label rather than being appended to it (`312 leads · 7 folders` where it used to read `312 leads · All folders`; in the checkbox-selection branch it *is* appended, as `312 selected leads · 7 folders`), and each format's hint changes ("One sheet per folder — every field", "Every field — grouped by folder", "Print-ready — split by folder").
- **Verified by actually running the writer**, not by eyeballing it — but *structurally only*: a scratchpad harness transpiled the TS with the project's own `typescript`, stubbed the DOM, captured the `Blob`, and the resulting `.xlsx` was unzipped with .NET's `ZipFile` — 3 folders produced `sheet1..3.xml` with matching rels and content-type overrides. No spreadsheet application was ever opened on the file.
- **Lint never ran.** `next lint --file` rejected the flag and bare `npx next lint` treated `lint` as a directory name. Only `tsc --noEmit` (exit 0) actually gated the change.

## Narrative

The session opened by orienting on the Leads tab. `components/apmg/LeadsPage.tsx` renders `<StoredLeadsPanel refreshSignal={0} enableGlobalSearch />`, and inside `StoredLeads.tsx` that flag routes the landing surface to `AllLeadsView` — a search bar + folder dropdown sitting above the folder grid. `AllLeadsView` already fetches **every** lead once via the flat `GET /api/pipeline/leads` (no `batch` param) and filters client-side, so the rows needed for an all-folders export were **already in memory** on that surface. That made the first ask cheap: the grid didn't need a new fetch, just a prop.

Reading `lib/pipeline/leadExport.ts` reframed the request. The file's own header comment describes it as "Client-side lead exports — CSV, XLSX and PDF — with zero dependencies, mirroring the TelemetryReportExport approach (the one existing export)" — i.e. the Export popover, the RFC-4180 CSV, the hand-written OOXML workbook and the print-window PDF were all pre-existing work. What was missing was the *folder* dimension: the workbook hard-coded a single `<sheet name="Leads" sheetId="1" r:id="rId1"/>`, `rId2` for styles, and one `xl/worksheets/sheet1.xml` part.

The work went format by format.

**Grouping first.** A `folderKey()` helper plus `groupLeadsByFolder()` and `leadFolderCount()` were added, sorting folders alphabetically with the `Ungrouped` bucket forced last. The `__ungrouped__` sentinel had to be duplicated into the file with a `// keep in sync with UNGROUPED in lib/pipeline/server.ts` comment — that constant now exists in three places (`lib/pipeline/server.ts:287`, `StoredLeads.tsx:33`, `leadExport.ts:67`), which the comment acknowledges rather than fixes.

**XLSX** was the real change. The single-sheet body was extracted into a reusable `worksheetXml(rows)` (frozen bold header, per-column widths, inline strings), and `exportLeadsXlsx` became a loop: sheets are derived from the groups, sheet names run through `safeSheetName`, and the workbook part, `xl/_rels/workbook.xml.rels`, `[Content_Types].xml` overrides and the ZIP entry list are all generated from that array. The styles relationship ID moved from a hard-coded `rId2` to `rId${sheets.length + 1}` so it can't collide with the worksheet rels — the kind of off-by-one that would produce a workbook Excel silently refuses to open.

**CSV** got the honest treatment: a flat file has no sheets, so a multi-folder export is at least emitted folder-by-folder, with a comment saying exactly that and pointing at the `Folder` column as the actual carrier of the split. **PDF** got a `tr.grp` heading row per folder (grey band, uppercase, `break-after: avoid` so a heading can't strand at the bottom of a page), the row renderer refactored out into a `leadRow()` closure so it could be reused per group, and the lede line now says "grouped into N folders … the workbook puts each folder on its own sheet".

**Then the UI.** `LeadsExport.tsx` imports `leadFolderCount`, derives a `multiFolder` flag, and switches both the scope line and all three format hints on it. In `StoredLeads.tsx`, `FoldersView` gained an optional `exportRows?: LeadView[]` prop; `AllLeadsView` passes its already-loaded `rows`, and the Refresh button was wrapped in a `flex` row with `<LeadsExportMenu rows={exportRows} scope="All folders" />` in front of it. The prop is deliberately optional: the **Pipeline** import flow renders `FoldersView` directly (`StoredLeads.tsx:130`, `enableGlobalSearch` false) with no rows loaded, so the button simply doesn't render there — documented in the prop's JSDoc.

**Verification was the interesting part.** Writing a ZIP by hand and *believing* it works is exactly the failure mode this repo's docs keep recording, so the workbook got exercised for real. There was no TS runner in the project (`node_modules/.bin` had no `tsx`/`esbuild`/`ts-node`; Node v24.18.0), so a scratchpad harness required the project's own `typescript` to transpile `leadExport.ts` and ran it under Node with tiny DOM stubs that captured the `Blob` instead of downloading it. First run failed — `require("typescript")` resolved relative to the scratchpad directory, not the project — fixed by requiring an absolute `node_modules/typescript` path. It then wrote a 12,633-byte workbook from a fixture with three folders, one of them deliberately hostile: `a/very*long?folder[name]:that-needs-truncating-badly`. PowerShell + `System.IO.Compression.ZipFile` unzipped the output and confirmed the parts list (`[Content_Types].xml`, `_rels/.rels`, `xl/workbook.xml`, `xl/_rels/workbook.xml.rels`, `xl/styles.xml`, `xl/worksheets/sheet1–3.xml`), the sanitised/truncated sheet names in `xl/workbook.xml`, and `sheet2.xml`'s frozen pane + column widths. A single-folder run was checked too, and still produced one `Leads` sheet.

`npx tsc --noEmit` passed. Two attempts to lint the changed files both failed on tooling, not on code: `next lint --file …` → `error: unknown option '--file'`, and plain `npx next lint` → `Invalid project directory provided, no such directory: …\leadgen\lint` (Next.js parsed `lint` as a positional path). Lint was left un-run rather than faked, and the session ended there — the user never replied.

## Decisions
- **Reuse `LeadsExportMenu`, don't build a second export UI.** The folder grid mounts the exact same popover the in-folder table uses, so CSV/XLSX/PDF, filenames, telemetry (`leads_export_open`, `leads_export_{csv,xlsx,pdf}`) and the popup-blocked error path all behave identically in both places.
- **Stay dependency-free.** The obvious move was `npm i xlsx`. The existing writer already produced a workbook Excel accepts, so multi-sheet was done by parameterising it — the diff is +125/−20 lines in one file (`git diff --numstat`) and zero bytes to the bundle's dependency graph.
- **Split only when it's a split.** `groups.length > 1` gates every behaviour change. A one-folder export is output-equivalent to before (sheet named `Leads`, no PDF headings, original CSV row order — the only difference anywhere is an unused `tr.grp` CSS rule now sitting in the PDF's stylesheet), so the common case can't regress.
- **`exportRows` is optional, not required.** Rather than teach `FoldersView` to fetch leads itself, the caller that already has them supplies them. The Pipeline import flow, which doesn't, just loses the button — no empty exports, no duplicate fetch.
- **CSV keeps one file.** Multiple CSVs (or a zip of them) was rejected in favour of folder-ordered rows plus the existing `Folder` column, and the code comment says why. The user asked for sheets; only XLSX has sheets.
- **`Ungrouped` sorts last** everywhere (grouping, sheet order, PDF sections), matching how the folder dropdown in `AllLeadsView` already sinks the null-`batch` bucket.
- **Verify by generating and unzipping, not by reading the code.** Hand-written OOXML is exactly the kind of thing that looks right and opens broken, so the writer was executed and its output inspected part by part.
- **Report the lint failure instead of hiding it.** Both lint invocations were tooling errors; the change shipped on `tsc` alone with that stated.

## Problems / gotchas
- **`next lint` is unusable as invoked here.** `--file` is not a recognised option, and `npx next lint` interprets `lint` as a project directory (`no such directory: …\leadgen\lint`). `package.json` still declares `"lint": "next lint"`, so that script is likely broken too — nobody has linted these files. Worth sorting out separately (this project is on Next 16, where `next lint` was removed).
- **No TS runner in the project.** Verifying a `.ts` module under Node required transpiling it manually with the project's `typescript` package. The first harness run died on `Cannot find module 'typescript'` because `require` resolved from the scratchpad directory — fixed with an absolute path into the project's `node_modules`.
- **The `__ungrouped__` sentinel now lives in three files** (`lib/pipeline/server.ts:287`, `StoredLeads.tsx:33`, `leadExport.ts:67`), each with a "keep in sync" comment. It is a latent drift hazard rather than a bug today.
- **Two subtly different folder keys.** The exporter uses `r.batch?.trim() || UNGROUPED`, while `AllLeadsView`'s dropdown uses `r.batch ?? UNGROUPED`. A lead whose `batch` is whitespace-only would be filed under `Ungrouped` by the export but shown as its own folder in the dropdown. Not observed in real data; noted because the two are meant to agree.
- **`safeSheetName` covers the rules that were tested, not every Excel rule.** Illegal characters, the 31-char cap and duplicate names are handled and were exercised with a hostile fixture. Excel's reserved `History` name and its ban on leading/trailing apostrophes are **not** special-cased.
- **The export is capped at 10,000 rows.** `app/api/pipeline/leads/route.ts` pages through PostgREST (`PAGE = 1000`) but bounds one response at `LIMIT = 10000`, so an "All folders" export can never exceed that regardless of how many leads Supabase holds. Silent ceiling — nothing in the UI says so.
- **Selection and search still win over folders.** The popover exports whatever the caller scoped it to; sheets are derived from the folders that survive the checkbox selection / search filter, not from the folder list. On the grid this is moot (the grid only shows when there is no search and no folder filter), but on the flat results table a filtered export can legitimately produce fewer sheets than there are folders.
- **The grid's Export button is gated on `exportRows.length > 0`** — an empty lead database therefore gets a folder grid with no Export button at all (`StoredLeads.tsx:882`). It is *not* a late-mount, though: `AllLeadsView` only renders `FoldersView` from inside its `state.status === "ready"` branch (`StoredLeads.tsx:323`, `:358–360`) and shows a `TableSkeleton` while the leads fetch is in flight, so by the time the grid exists the rows are already in hand — the button mounts with the grid's header, in fact *ahead* of the folder tiles, since `FoldersView` then runs its own `/api/pipeline/batches` fetch.
