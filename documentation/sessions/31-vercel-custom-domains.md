## Decisions
- **Subdomains, never the apex.** `apmgservices.com.au` and `www` serve APMG's live marketing site — from a *different Vercel account*, as it turns out, not another host; the repo bakes those URLs into outbound email and the portal footer. Only new subdomains get bound to this app's project(s).
- **`customer.` accepted over `portal.`/`go.`/`hello.`** — the user's call; the assistant registered the "prospects aren't customers yet" objection once and did not relitigate it. Technically identical either way.
- **Two hostnames, not one** — `admin.` for the console, `customer.` for the prospect-facing surface — even though one codebase serves both. This matters more than the session credited it (see gotchas): the host split is what the existing `middleware.ts` host-wall keys on.
- **`NEXT_PUBLIC_TRACK_BASE` as a Vercel env var plus a redeploy** — no source edit, because the send route already prefers it over the request origin. The session called this "the only code-side change needed", which is **incomplete**: the new customer host must also go into `CUSTOMER_PORTAL_HOSTS` on the customer project (see gotchas), and `portalBase` in the n8n Split Messages node still hard-codes the old host.
- **Keep the `_vercel` TXT records until Vercel goes green**, then optionally delete them — they're a one-time ownership proof, and Vercel says so itself.
- **Defer the docs/n8n hostname sweep** rather than rewrite reference files twice — framed as waiting on a confirmed hostname, though the user had already said `customer.`; in practice it waits on DNS actually resolving.
- **Verify DNS from the authoritative nameservers rather than trusting either party.** Evan's singular "the CNAME and TXT record" plus Vercel's badge were both treated as claims to check, not facts — which is the only reason the failure was caught the same morning instead of after a Refresh-and-wait cycle.

## Problems / gotchas
- **The domain was already claimed on another Vercel account — confirmed, not just a screenshot claim.** `www.apmgservices.com.au` is a CNAME to `5af2fa291c28a111.vercel-dns-016.com` and returns `Server: Vercel` with `X-Powered-By: Next.js`; the apex `307`s to it, also from Vercel. APMG's marketing site is therefore a Next.js app on somebody else's Vercel account, and that is what forced the `vc-domain-verify` TXT step. Evan didn't know whose account it is and pointed at Zac; **whose it is remains unanswered** — the obvious lead is whoever built/hosts the marketing site.
- **Two of the four record values were never captured.** The `customer` subdomain's CNAME target and its `vc-domain-verify` string were cropped out of the user's screenshot, so both the instructions and the email to Evan carry `[paste from Vercel]` placeholders. Anyone resuming this must re-open the customer domain's "DNS configuration" panel — the values are per-domain opaque hashes and cannot be derived from the admin ones (compare `f778065ba5edfa19.vercel-dns-017.com` issued for `admin.` with the unrelated `5af2fa291c28a111.vercel-dns-016.com` that the marketing site's `www` uses). Confirmed unrecoverable from the transcript or the repo: they appear nowhere in either.
- **The records were added to the wrong zone.** Verified live from `8.8.8.8` while writing this doc: `admin.apmgmaintenance.com.au` → `CNAME f778065ba5edfa19.vercel-dns-017.com` exists, while `admin.apmgservices.com.au`, `customer.apmgservices.com.au` and `_vercel.apmgservices.com.au` all return NXDOMAIN from GoDaddy's own `ns51.domaincontrol.com`. The two domains are easy to confuse — `apmgmaintenance.com.au` is the outreach/sending domain (in use since session 18, 2026-07-12; only the `outreach@` **mailbox** on it is a day old).
- **The TXT record is also malformed.** On `apmgmaintenance.com.au` the root carries a TXT whose value is `_vercel vc-domain-verify=admin.apmgservices.com.au,20d3dd56440eaf82ad59` — the record **name** was pasted into the **value** field. So even on the right zone it would not have verified. **Vercel verification never succeeded**, and this leftover record should be deleted (session 32 picked it up in a DNS audit).
- **Only the `admin` pair ever landed anywhere.** Consistent with Evan's singular phrasing: there is no `customer` CNAME and no customer verify TXT on either zone (re-checked on both `apmgservices.com.au` and `apmgmaintenance.com.au`).
- **The wrong person may have been asked.** The advice and the email routed the change through Evan/Enabla. Session 32's record — Evan's own "DNS isn't hosted by us", carried into the `outreach-mailbox-provisioned` memory note — states DNS is **not** managed by Enabla — **Zac holds registrar access and the MFA**, and DNS changes should go through him. That is consistent with edits landing on the zone Enabla does touch (`apmgmaintenance.com.au`) rather than the one asked for.
- **`cname.vercel-dns.com` vs the project-specific target.** The first answer gave the generic legacy CNAME value; Vercel's panel actually issued `f778065ba5edfa19.vercel-dns-017.com.`. Always copy the value out of the Vercel panel rather than reusing a remembered one.
- **"One Vercel project" framing is wrong.** The session's opening answer said the portal and dashboard are "the same Next.js project on Vercel," so "one project + two DNS records." The repo's record contradicts that four ways: `middleware.ts:4-21` — *"The admin console lives on its own Vercel project/domain; the customer portal is a SEPARATE Vercel project bound to a customer host."*; doc 18's deploy checklist and doc 24's follow-up both say to set `CUSTOMER_PORTAL_HOSTS` and friends **"on the customer Vercel project"**; and two distinct hostnames are in play (`apmg-app.vercel.app`, the original admin/tracked host from doc 08, vs `customers-apmg-services.vercel.app`, the customer portal). `.vercel/project.json` links this checkout to project **`ampg-leadgen`** alone, so "add the domain in Vercel → your project" would have put *both* hostnames on whichever single project the user had open. Each subdomain must be added to the project that actually serves that surface, and `NEXT_PUBLIC_TRACK_BASE` set on the right one. Never reconciled in-session.
- **Unflagged security consequence: the host wall would not cover the new domain.** `middleware.ts` recognises customer hosts only from `CUSTOMER_PORTAL_HOSTS` (default `customers-apmg-services.vercel.app`) or `CUSTOMER_PORTAL_HOST_SUFFIX`, and it **deliberately fails open to the full app for unrecognised hosts**. If `customer.apmgservices.com.au` is attached without adding it to `CUSTOMER_PORTAL_HOSTS`, the admin dashboard and `/api/pipeline/*` would be reachable on a public, prospect-facing domain — exactly the hole doc 18 closed. The session never mentioned this.
