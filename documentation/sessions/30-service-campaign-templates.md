## Narrative

**Reconnaissance.** The session opened by mapping the compose flow rather than guessing at it: `components/apmg/pipeline/SendCampaigns.tsx` (a large single-file stepped flow, `ComposePanel` at line ~1639 pre-change), `lib/pipeline/campaign.ts` (the pure template/merge module shared by client preview and server render), the compose and send routes, `lib/ai/composeEmail.ts` + `lib/ai/composePrompt.ts`, and `lib/pipeline/sectorStore.ts`. A grep for image handling in `app/api/pipeline/campaigns/**` came back with **no matches** — which is exactly the finding that shaped the design: the app never handled the email's imagery at all. The branded HTML (header, brand band, hero band, PDF card, footer, unsubscribe button) is built inside the n8n **Split Messages** code node, whose hero was a hardcoded `BRAND.hero` team photo. So "make the image match the service" was necessarily a two-sided change: a new field on the webhook payload, plus an edit to the node.

The service copy source was also settled here. `ServicesPortal.tsx` carries the service descriptions **mirrored verbatim from apmgservices.com.au/services** (with a comment saying to edit the site, not the file). Those descriptions became the sole factual basis for the template copy and the AI `focus` strings — no new claims invented. The portal list turned out to be a `general` pseudo-entry plus exactly 8 services, matching the user's "8 services" count.

**Build order.** `lib/pipeline/services.ts` first, as a pure framework-free module in the same spirit as `campaign.ts`, so one definition list drives the client picker, the compose route's prompt suffix, and the send route's hero URL.

Then the AI path. The important call was *where* the service focus goes. Putting it in the system instructions would have collided with two existing pieces of the system: the Supabase `compose_prompt` row that overrides the code's system prompt, and the stable KB prefix that prompt caching depends on. So `draftEmail()` gained an optional `serviceFocus` parameter that is concatenated onto the per-lead user message alongside the existing rotating writing angle, and the compose route builds that string in `serviceFocusPrompt()`. The instruction tells Claude to make the service the star **and** tailor it to the recipient's sector, with two concrete examples in the text — flooring for an early learning centre as safe, non-slip floors where children play, and electrical for aged care as safe, compliant power for residents — plus a rule that the subject and CTA label must both fit the service *and* the sector.

The deterministic fallback was threaded next: `demoDraft(lead, service?)` early-returns the service's subject and `{{business}}`-merged HTML when a service is active. All **five** `demoDraft` call sites in the compose route (the `base` inside `draftForLead`, demo mode, the pre-gate deadline bail, the post-gate deadline bail, and the `withDeadline` fallback value) were updated to pass the service, so a timeout or a Claude miss can't silently drop back to the generic multi-trade pitch mid-batch.

The send route then resolved the hero server-side — `serviceBySlug(body.service)` → `publicObjectUrl(SECTOR_ASSETS_BUCKET, service.image)` → `hero` / `hero_alt` on each message, both `undefined` (and therefore dropped by `JSON.stringify`) when no service was picked or Supabase isn't configured. The client never sends a URL, only a slug.

**UI wiring** was the largest single chunk: a `service` state string (`""` = general), a `composedServiceRef` to detect stale drafts, an invalidation `useEffect`, the service prefixed onto the resume key, `service` added to the compose and send POST bodies and to both `useCallback` dep arrays, a `selectService()` handler that fills subject/body, `resetFlow` handling, `serviceName` threaded into `DraftsReviewPanel` and `ReviewPanel`, and the chip row itself in `ComposePanel`. One self-correction happened mid-stream: `resetFlow` initially reset subject/body unconditionally, which would have clobbered a hand-written custom template — it was immediately changed to only reset them `if (service)`.

**The n8n side.** `buildHtml()` gained `hero`/`heroAlt` parameters, `BRAND` gained a `heroAlt` default string, and the per-message read is `const hero = (m.hero || BRAND.hero || "").toString()` — so an un-updated payload renders exactly as before. A small scratchpad Node script then wrote the patched JS into the `Split Messages` node's `jsCode` inside `references/APMG Campaign Send (clean).json`, reporting a 10,876-char body.

**The image pipeline, and the one real dead end.** A scratchpad PowerShell script converted `app/services/*.png` (407–864 KB) to email-sized JPEGs via `System.Drawing` and upserted them into the `sector-assets` bucket with the service-role key. Adding `[Net.ServicePointManager]::SecurityProtocol = [Net.SecurityProtocolType]::Tls12` fixed it, and because the uploads are upserts the rerun was safe. All 8 uploaded, and a HEAD request on `services/flooring.jpg` confirmed `200 image/jpeg 45543 bytes`.

## Decisions
- **The service focus rides the per-lead *user* message, not the system prompt.** Two reasons, both pre-existing constraints: the Supabase `compose_prompt` row overrides the code's system instructions (so anything added there could be silently ignored on the live install), and the KB system block must stay byte-stable for prompt caching. This is the single most important design choice in the session.
- **The hero is resolved server-side from a slug.** The client posts `service: "<slug>"`; the send route derives the public Storage URL. The browser never supplies an image URL, so a tampered client can't inject an arbitrary image into an outgoing email.
- **`hero`/`hero_alt` are optional with a fallback.** An un-patched n8n node, an unknown slug, or an unconfigured Supabase all degrade to today's exact behaviour (default team photo) rather than a broken or missing hero. That is what makes the outstanding n8n paste non-blocking.
- **Copy grounded only in the verbatim portal descriptions.** Template bodies and `focus` strings restate only what apmgservices.com.au/services already claims, in the voice already established by `DEFAULT_BODY_HTML` (natural Australian English, no em dashes, the "who's the best person to speak to" ask, a short service-specific CTA label such as *"Flooring, done right"*).
- **8 templates, not 9.** The picker's *All trades (general)* chip covers what the portal calls "General enquiry", so the 8 chips map 1:1 onto the 8 real service lines. `app/services/preventive.png` has no matching portal service and was deliberately left out.
- **Reuse `sector-assets` rather than a new bucket**, and convert PNG → email-sized JPEG (41–90 KB, down from 407–864 KB PNGs) rather than shipping portal-weight images into inboxes.
- **Switching the template invalidates ready drafts but keeps the batch plan** — the batches are audience slices and stay valid; only the copy is stale. The service is also prefixed onto the partial-resume key so a resumed run can never mix drafts written for two different services.
- **`resetFlow` only restores the default subject/body when a service was active**, so a hand-written custom template survives a reset.
- **Arial in the email font stack left as-is** despite the design hook flagging it — email clients can't reliably load webfonts, and the stack predates this session's change.

## Problems / gotchas
- **PowerShell 5.1 TLS default broke the uploads.** `Invoke-RestMethod` died with *"The underlying connection was closed: An unexpected error occurred on a send."* after converting the first image. Fixed by forcing `Tls12` on `ServicePointManager`; the rerun was safe because the Storage writes are upserts.
- **`npx tsc` through PowerShell reported a `NativeCommandError`** purely because npm writes notice lines to stderr. Re-running through Bash gave the clean result. Worth remembering: on this box, typechecks are more legible via the Bash tool.
- **The artifact build stalled.** The first `node build-preview.js` call recorded no output, and it took two user "continue" turns before the script reported `built 211 KB` and the page published — the first of those turns produced no assistant action at all ("No response requested"). No code fault was identified — it reads as a harness/turn hiccup, and the second invocation of the identical command worked.
- **n8n runs its *saved* copy of the code node.** Editing `references/split-messages.node.js` (and the workflow JSON) changes nothing about live sends until the code is pasted into the node in the live workflow. This is the same trap that cost a multi-round debug in Session 18 — flagged explicitly this time instead of being discovered.
- **This session named the wrong n8n tenant.** Every in-session reference to the live workflow said `apmg.app.n8n.cloud`, taken on trust from `N8N_BASE_URL` in `lib/data/integrations.ts`. Session 32 proved that host 404s and that the real tenant is `apmgau.app.n8n.cloud`. Nothing this session *built* depends on the hostname (the send route resolves the POST target from `app_settings` server-side), but the handover instruction pointed at a tenant that does not exist — and so does the `service-campaign-templates` memory file written here. See [doc 32](32-outreach-email-authentication-setup.md).
- **Picking a chip overwrites the shared subject/body** with the service's copy, including over hand-typed text. There is no confirm step; only `resetFlow` is careful about this.
- **The artifact's "Draft with AI" email is illustrative.** It is representative of what Claude writes for a childcare lead, not a stored draft — the wording will differ per lead.
- **One service per send.** `service` is a single top-level field on both POST bodies, so a single send/compose run pitches exactly one service; a mixed-service blast means separate runs.
- **Everything is uncommitted.** `lib/pipeline/services.ts` is untracked and the other seven files sit as unstaged modifications on `main`, mixed in with unrelated in-flight work from adjacent sessions (`lib/pipeline/notifyEmails.ts`, `LeadsExport.tsx`, `IntegrationsPage.tsx`, and others). Nothing here has been committed or deployed.
