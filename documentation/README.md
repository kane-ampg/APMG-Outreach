## Project snapshot

*Rewritten 2026-07-30 against the live repo.* **APMG Leadgen** is a cold-outreach lead-generation system for **APMG Services**. One Next.js codebase ships **two deployments**: an internal role-gated console (import leads → AI-compose outreach → tracked links → sales queue) and the **public customer portal** that email recipients land on, walled apart by hostname in `middleware.ts`.

- **Stack:** Next.js 16 (App Router, Turbopack) · React 19 · TypeScript · Tailwind CSS 3 · `motion/react` for animation · `lucide-react` icons · **Supabase** (Postgres via PostgREST, plus a `sector-assets` Storage bucket) · **`@anthropic-ai/sdk`** — `claude-opus-4-8` for campaign drafts and sales briefs (allow-listed `COMPOSE_MODEL` override: opus-4-8 / sonnet-5 / haiku-4-5), `claude-haiku-4-5` for the public portal chat · **n8n** for every outbound side effect (campaign send, email finder, enquiry notification). No test framework and **no ESLint config** — `next lint` is a dead script on Next 16, so verification is `tsc --noEmit` + `next build`, with `playwright` as a dev dependency for screenshots.
- **Look & feel:** A black/red "Signal" telemetry-console aesthetic, **dark-mode by default** with a light toggle. Follows the `ui-standards.md` design grammar (adapted from "Simple HRIS"). The public `/portal` is the deliberate exception — a **light-only** trust surface, pinned by a pre-paint script in `app/portal/layout.tsx` that strips the dark class without touching a staff member's stored `apmg-theme`. Console browser-tab titles are per-surface via `APP_NAME` / `tabTitle()` in `lib/nav.ts`; the portal keeps its customer brand.
- **Access control:** three layers, one of which is an explicit stand-in.
  - **Permission-first RBAC** — roles (`admin` / `client` / `sales`) are bundles of atomic `resource.action` permissions; every gate checks a permission, never a role (`TAB_PERMISSION`, `landingTab`). All three roles are now enabled, and `sales` lands on its own queue rather than the Overview.
  - **A stand-in sign-in** at `/login`: `lib/auth/users.ts` is a hard-coded five-person directory behind one shared plaintext password, writing client-readable `apmg-role` / `apmg-user` cookies that `lib/rbac/server.ts` reads to guard route handlers. Both files say so in comments — it is **not** a security boundary, and real Supabase auth is still the largest outstanding item.
  - **A host wall** in `middleware.ts`: any host in `CUSTOMER_PORTAL_HOSTS` (default `customers-apmg-services.vercel.app`) is served `/portal`, `/t/*` and `/api/portal/*` only — stray pages redirect to the portal, non-portal APIs hard-404. It fails **open** for unrecognised hosts, so a new customer domain must be added to that env var *before* it is pointed at the app.
- **Instrumentation:** `data-track` click telemetry with a live in-app inspector (in-memory ring + localStorage, batched to `NEXT_PUBLIC_TELEMETRY_ENDPOINT` when set). Server-side, `public.portal_events` is the single ledger: attribution clicks from `/t/[id]`, portal views / service-opens / social clicks, one `email_sent` row per delivered email, `chat_prompt` quota rows, and enquiries. Operator traffic (the `apmg_internal` cookie stamped on dashboard page loads) and bots/link-scanners (by UA) are filtered out so the funnel counts real prospects only. Traffic source is captured in middleware into an `apmg_src` cookie (from `?utm_source=` or a recognised social `Referer`) and stamped **server-side** onto every event and stored enquiry.
- **Surfaces — internal console** (`app/page.tsx` → `DashboardShell`; 13 permission-filtered tabs across Portal / Monitor / Sell / Automate / System):
  - **Our Services** — the customer portal rendered inside the console.
  - **Overview** — **role-aware**, with KPI cards reading the **live** Supabase `public.leads` data (via `useLeadStats`), a Week/Day/Month auto-cycling histogram, and a recent-leads table.
  - **Pipeline** — **Leads** (an n8n-style stepped importer that ingests the Bing-scraper CSV, asks "Save leads?", and writes **live** to Supabase) and **Send Campaigns (Automation)**: pick emailable leads, optionally choose one of the 8 per-service templates (`lib/pipeline/services.ts`, hero JPEGs in the `sector-assets` bucket), AI-compose per lead (server-paced under the single `COMPOSE_RATE` knob), then send via the n8n webhook with every CTA rewritten to `/t/<lead>?c=<campaign>`. A separate **No email** tab hosts the n8n email finder (`MAX_FIND_LEADS = 50`).
  - **Leads** — a folder browser over the stored Supabase leads (per-upload "folders", multi-select delete, per-lead detail modal) plus CSV / XLSX / PDF export with one worksheet per import folder.
  - **Enquiries** — inbound portal enquiries with status triage, a "Where they came from" source rollup and per-enquiry "via TikTok" chips.
  - **Sales** / **Closed deals** — a paginated queue of every lead that has been emailed (gated on the `email_sent` ledger, served by `/api/sales/queue`), Claude-backed AI briefs, and a guided **Closed** flow. *(Queue data is live; contacted/closed statuses are still session-only.)*
  - **Integrations** (Automate) — the n8n automation registry (campaign send, email finder, enquiry notification) as a connection bar + card grid, plus the enquiry-notification recipient list (`MAX_NOTIFY_EMAILS = 10`, one comma-joined send).
  - **Sector Playbooks** — three sectors (`aged-care`, `early-childhood`, `education`) mapping a lead's CSV Category to a knowledge-base markdown + PDF; the KB grounds every AI draft, and an uploaded `.md` overrides the repo file.
  - **Email Composer** — edits the exact compose prompt, persisted to the `public.compose_prompt` singleton; a saved row overrides the in-code default.
  - **Legal Documents** — publishes and versions the portal's Terms & Privacy. Until a real (non-placeholder) version is published, the enquiry route refuses to store PII by design.
  - **Telemetry** — funnel + per-lead trail inspector with a PDF report export.
  - **Settings** — still a `ComingSoon` placeholder.
  - Sidebar navigation (permission-filtered, with live Pipeline / Sales counts and a Telemetry badge that fires on unseen *customer* activity only), a dynamic-year footer, and an APMG favicon.
- **Surfaces — public portal** (`/portal`, light-only, customer-branded):
  - A photographic hero with a logo top bar and a phone / **WhatsApp** CTA row (`1300 97 97 40`, single-sourced from `lib/legal/company.ts`), a fact-only `PROOF_POINTS` band, and three in-page sliding-pill tabs: **Our Services** (8 service cards + a general enquiry), **Google Reviews** (a hand-transcribed 20-review snapshot in `components/apmg/googleReviews.ts`) and **Our Team** (the 8-person crew roster with self-hosted headshots).
  - A per-service **Enquire** modal carrying the client's own published service description + inclusions, a **fail-closed, server-authoritative consent gate** pinned to the current legal version, and a honeypot. The old entry-time `PortalConsentGate` is kept in the repo but unmounted.
  - A **Haiku chat bubble** with a durable **10-prompt lifetime allowance** per visitor (`chat_prompt` rows in `portal_events`), behind a stack of gates (same-origin → bot filter → per-IP rate limit → input caps → configured-key check → quota slot → daily circuit-breaker → KB-only prompt) and a `PORTAL_CHAT_DAILY_CAP` kill switch.
  - Facebook / Instagram / TikTok links (`COMPANY.socials`, tracked as `portal_social_click`), a **legal-doc modal** over `/api/portal/legal` with `/portal/terms` + `/portal/privacy` still live as full pages, a KB-grounded FAQ, a contact card, and a Spam Act **unsubscribe** flow (`/api/portal/unsubscribe` writing `email_suppression`, which the send route filters against).
- **Live vs. pending:**
  - **Live:** Supabase lead storage (thousands of rows imported), the n8n campaign-send / email-finder / enquiry-notification webhooks, `portal_events` telemetry, the consent gate, unsubscribe suppression, and the customer portal on `customers-apmg-services.vercel.app`. The `outreach@apmgmaintenance.com.au` mailbox exists and its SPF / DKIM / DMARC records are verified live in DNS.
  - **Pending:** **real auth** (the `/login` directory and `apmg-role` cookie are stand-ins; the Supabase service-role key sits behind a same-origin floor only); the `portal_inquiries.source` migration in `supabase/portal-telemetry.sql` is **unrun**, so enquiry source degrades silently; the company **ABN / legal entity is still `null`** and the insurance / licence / WWCC proof lines are unwritten; DMARC has no `rua=`, Google-side DKIM signing was never confirmed, and the outreach mailbox has had no warm-up and no test send; the branded `admin.` / `customer.apmgservices.com.au` domains never verified (the DNS records landed on the wrong zone); `N8N_WEBHOOK_SECRET` is unset so the campaign webhook is anonymous, and the send path has no pacing (`MAX_RECIPIENTS = 1000`, no Wait/Loop node); the per-service hero images stay inert until the updated `references/split-messages.node.js` is pasted into the live n8n workflow; and the work in docs 28, 29 and 30 is still uncommitted on `main`.
  - **Never observed green:** no session has ever seen a successful production build *on the customer Vercel project*. The only build log in the record is the **failed** one for `35dcaf5`; the fix shipped in `a5cc0c0` and nobody confirmed the redeploy. So every "shipped to the portal" claim in docs 19–26 is a claim about `main`, not about what a prospect sees.
  - **Two known-wrong constants, both operator-facing:** `N8N_BASE_URL` in `lib/data/integrations.ts` is `https://apmg.app.n8n.cloud`, a host that returns **404** — the live tenant is `apmgau.app.n8n.cloud`. It only feeds the Integrations tab's "Manage" / "Open in n8n" links and the URL placeholder (the POST target is resolved server-side from `app_settings`), but it sends the operator to the wrong tenant and suggests a wrong URL to copy. ## How this documentation was produced

The session transcripts live as JSONL files under Claude Code's project store. Each was condensed deterministically (user messages, assistant reasoning, tool calls, truncated results, plus an auto-extracted "files touched" list), then analysed against the **live repo**. The 2026-06-30 refresh used parallel analysis agents to compute the *delta* between each large transcript and its existing doc, then authored docs 07–12 from those verified reports. The **2026-07-30 refresh** repeated that pattern across the last 20 sessions and added a separate fact-checking pass that re-tested every claim against the tree as it stood that day — which is why docs 19–32 state plainly what was *not* verified (browser-checked, deployed, executed) and carry explicit "still open" lists.

**Maintaining this folder:** when a future session does meaningful work, add a new `sessions/NN-*.md` (same template) and a row to the index above. If a session that already has a doc *continues* and does substantially new work, add a new numbered doc that shares its Session ID and cross-reference both ways (as 07/08 do with 01, and 09 does with 03).

Two conventions were added by a **2026-07-30 completeness audit** over the whole set, and are worth keeping:
- **Concurrency is declared in the header.** Where sessions overlapped in time or shared a commit, each doc carries a `> **Shares its commit with:** …` / `> **Ran concurrently with:** …` line linking the siblings. Without it, a mixed commit reads as one session's work and the docs quietly disagree about who wrote what. Docs 19–32 now all carry this where it applies.
- **Superseded content is annotated in place, not rewritten.** A doc records what its session did; when later work reverses or overtakes it (doc 19 undoing doc 16's console styling, doc 32 overtaking doc 29's deliverability state, doc 32 replacing doc 30's n8n hostname), the older doc gets a clearly-dated "superseded / host correction / drifted since" note that links forward. Doc 18 additionally carries a **"Where these follow-ups went"** table, because it is the origin of most of the project's standing ops debt.

Note on template drift: docs 14/16/18 predate the current template and use `Key decisions` / `Problems hit` / `Outcome` where docs 19–32 use `Decisions` / `Problems / gotchas` / `Final state`. The content maps 1:1; only the headings differ.
